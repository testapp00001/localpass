# Phase 5.3 security review (started 2026-10-22)

Findings of the final review, by area. One section per reviewer, appended in order. The state reviewed is the
code after Phase 5.2 (the fixes) and 5.1 (property tests). The repo has no commits, so the review is by area.

## Rules for reviewers (read first)

Scope and skips:
- Review whether the code is *correct and complete*, especially the fixes made in Phase 5.2 (what changed is
  described in `docs/phase5-hardening-notes.md` sections 5.5, 5.5b, 5.5c; the original issue list V1-V26 and
  suspected items S1-S10 are in sections 5.1 and 5.2 of that file). A fix that is incomplete, bypassable, or
  that introduced a new problem is the most valuable finding.
- Skip the list "Checked and found sound" (notes section 5.3). Skip the user's settled decisions: V5 (Hello each time
  for cross-site fill and search), V7 (any process may ask to pair, the user approves the 6-digit code), V11/V22
  (ask before overwrite, port rule as pinned), V25 (Android refuses passkeys without a screen lock). Do not report
  these as findings.
- Threat model: a malicious web page or a malicious site's script, a hostile peer on the LAN, a malicious or buggy
  app on the same phone, a different user on the same PC. Malware running as the same Windows user is out of scope
  for the vault itself but in scope for "does not hand secrets out silently while the vault is unlocked".
- Read-only on production code. Do not edit anything except your own section of this file.

How to report (append your section at the end of this file; do not edit other sections):
- One entry per finding: `ID` (use `R<area>-<n>`, e.g. `RA-1`), **severity** (High / Medium / Low / Info),
  `file:line`, a concrete failure scenario (inputs or steps and the wrong outcome), how it was established
  (**ran** a test or experiment / **read** the code / **suspected**), and the test that would catch it.
- Also list, in one short paragraph, what you read and found sound, and which S-items you resolved (promote with
  evidence or drop with evidence).
- Be concrete and brief. No finding without a scenario. Prefer fewer, real findings over a long list.
- Your reply to the caller is at most 200 words: the count per severity and the ids of the High/Medium ones.

Machine safety (the user's PC is in use):
- Never touch, kill, rebuild or overwrite `target\release` or the running `localpass.exe`. Do not run `cargo` without
  `CARGO_TARGET_DIR=C:\app\projects\rust\local-pass\target\tmp\target-review`.
- Never re-register, unregister or change the Windows passkey provider package or its Windows settings. Never run
  setup/remove tests against the real package identity.
- Do not start browsers, emulators or the app unless your area says so. Leave no registry keys, temp folders
  (`%TEMP%\lp-*`) or processes behind. Never print `keystore.properties`, `*.jks`, or any secret.
- Never commit or push. Keep command output small (pipe through `tail`/`grep`).

**RA-1 (Medium, S1 promoted): page CSS can hide or move the in-page interface, so fill, passkey sheet and save bar can be clicked by the user without seeing them (clickjacking).**
- Where: `extension/src/content/ui.ts:48` (the host's inline style has no `!important`), activation handlers at `ui.ts:74-78`, `141-146`, `202`, `283`, `293` (no visibility or trust check; grep for `isTrusted|checkVisibility|elementFromPoint` over `src` is empty). Positions are predictable: save bar fixed at 12px/12px (`ui.ts:23`), sheet centred (`ui.ts:30-32`), badge at the field's right edge (`ui.ts:84-85`).
- Scenario: the attacker has script on an origin whose registrable domain has a saved login (XSS on the site, a sibling subdomain it controls; PSL private suffixes such as github.io do not count) and the vault is unlocked. The page ships `html > div:last-child { opacity: 0 !important; transform: translate(Xpx,Ypx) !important }` (an author `!important` rule beats the non-important inline style), a login form and `field.focus()` (no gesture needed), which shows the badge. A decoy button sits over the badge position (the page controls the field's rect). Click 1 opens the menu (positioned from the field's rect at reply time, which the page can move meanwhile); a second decoy sits over the first row. Click 2 sends `fill`, the worker answers a same-site `fillLogin` silently (`server.rs:802-826`, no Hello), and the password and TOTP code are written into the page's own form, which the page reads. The passkey sheet needs even less: `navigator.credentials.get()` opens it with no gesture, its backdrop covers the viewport and the row is centred, so one click on a decoy signs (Hello still asks while "ask for every passkey" is on). The save bar (also openable without a gesture, see RA-3) can be clicked the same way (adds a login for the page's own origin, or "Never for this site").
- Limits of the attack: the shipped root is closed (`dist/content.js:237`), so page script cannot click rows itself; the clicks must be the user's real ones. Needs two to three clicks at known places.
- Established: **read** and **ran** in happy-dom, which shows only the cascade and the missing checks, not real hit-testing: with that page rule the host's computed `opacity` is `0` and `transform` is `translate(40px, 40px)` while the inline style is unchanged, and a click on the row still sends `fill` and writes the password into the form. (The test root was open because `test/setup.ts` sets `__E2E__`, and happy-dom has no `isTrusted`, so none of this is evidence about synthetic versus real events.) The real-browser e2e from S1 was not run (rules).
- Test that would catch it: `e2e/run.ts` with a page stylesheet `html > div[style*="2147483647"]{opacity:0 !important}`: after the focus and the first click, `document.elementFromPoint` at the badge and at the first row must not leave the user clicking an invisible target (either the interface stays visible, or it refuses to act). Unit: every property of the host is set with `setProperty(name, value, "important")` (inline `!important` beats author `!important`; `all: initial !important` covers the rest) and activation re-checks `host.checkVisibility({ opacityProperty: true, visibilityProperty: true })`. Stronger: show the interface in the top layer (`popover`) so ancestors' opacity, filter and transform do not apply, and ask in extension-owned UI (the popup) before a page-initiated fill.

**RA-2 (Low): an extension-kind client can list every passkey with no user check.**
- Where: `crates/lp-broker/src/protocol.rs:215-217` (`provider_only` covers only `PasskeyAssertAny`), `server.rs:889`; the test comment at `crates/lp-broker/tests/server.rs:712` calls the listing "a provider operation", and `protocol_props.rs:96` pins it as provider-allowed, not provider-only. Nothing in `extension/src` sends `passkeyListAll`.
- Scenario: a same-user process reads the extension's secret (plaintext in the profile, the part of V26 that was left) and connects as the extension. While the vault is unlocked, `{"op":"passkeyListAll"}` returns rp id, rp name, user name, display name, credential id and user handle of every live passkey without a prompt, although V5 decided that listing the vault (`searchItems`) needs Hello every time. It also hands the process the exact sites to try with `findLogins`/`fillLogin`, which are silent for a client-claimed origin (design residual below).
- Established: **read**.
- Test: an extension-kind client sending `passkeyListAll` gets `forbidden`; the provider-kind tests (`listing_every_passkey_needs_an_unlocked_vault_and_never_prompts`) keep passing. Fix: add it to `provider_only`.

**RA-3 (Low): page-supplied sign-in values have no size cap, and a page can raise the save bar without a gesture.**
- Where: `extension/src/content/index.ts:152-166` (`capture`) and `168-195` (listeners on `submit`, click, Enter; they accept scripted events), `background/index.ts:139-146` (`storeCapture` writes the whole value to `storage.session`) and `119-124` (`fill` awaits `rememberFill`, another `storage.session.set`).
- Scenario: a page sets the password field to about 10 MB and dispatches `submit`. The value goes to the worker and is stored as `pending:<tabId>` until that tab closes or a page load finds it older than 2 minutes (`pendingFor`). `storage.session` has a 10 MB quota (Chrome), so other tabs' `fill()` (and the logins-list cache) can then fail with a quota error while the attacker's tab stays open. The same scripted submit makes the "Save this login" bar appear (1.5 s later when the page removes the form) with a page-chosen user name and password and no click, which RA-1 can then press. `saveLogin` itself is safe: `broker.ts:352` refuses frames over 1,000,000 bytes and the model caps a data op at 48 KiB (`lp-core/src/model.rs:17`).
- Established: **ran** (a scripted `submit` with a 5,000,000-character password is forwarded unchanged as `{kind: "capture"}`); the quota effect is **suspected** (the fake storage has no quota).
- Test: a content test that a 5,000,000-character value sends nothing (cap user name and password at a few KiB in `capture` and again in `storeCapture`, like `validate.ts` does for passkeys), and an e2e that fill still works in tab B after tab A did this.

**RA-4 (Low, functional): the in-page "Generate a strong password" row does nothing.**
- Where: `extension/src/content/index.ts:98-108` sends `{kind: "generate"}`; `background/index.ts:319-321` makes `generate` popup-only; `test/background.test.ts:41-56` pins that refusal for a page. The row's `.catch(() => {})` hides the `forbidden` answer.
- Scenario: on a sign-up form the user clicks "Generate a strong password"; nothing is filled and nothing is said. The popup does not call `generate`, so the feature has no working caller.
- Established: **read** plus the existing test (**ran**, passes). No test or e2e clicks the row.
- Test: a content test that the row fills every new-password box; fix by allowing `generate` for pages (it reveals nothing) or generating in the content script, and show the error.

**RA-5 (Low, S10 promoted; probably the app reviewer's area): an unreadable client file is treated as empty and the next pairing overwrites it.**
- Where: `app/src-tauri/src/broker.rs:31-47` (a read, `unprotect_local` or JSON failure ends in `unwrap_or_default()` at line 42, only a `warn!`), `insert`/`save` (`:63-65`, `:51-60`) write the same path.
- Scenario: DPAPI fails (or the file is damaged) at one start: the store is empty, every client gets `unpaired` (fails closed), and the first pairing (any process may ask, V7) replaces the unreadable file, so a file that a later start could have read is gone and the browsers and the Windows provider must all be paired again.
- Established: **read** (running it needs a build of the Tauri crate; not done).
- Test: write garbage at the path, `ClientFile::load`, `insert`; the old bytes must survive as `.bak` or the insert must be refused, and the Settings list should say the file could not be read.

**RA-6 (Info): `passkeyAssert` asks Windows Hello before anything is validated.** `server.rs:959-963` calls `verified()` (Hello) first; origin, rp id, hash length and item are checked only inside `Engine::passkey_assert` (`credentials.rs:675-701`). `passkeyCreate` (`passkey_would_replace` runs `passkey_can_create`) and forced fill do check first. **RA-7 (Info): the text shown in the "Replace?" dialog is cleaned of control characters only.** `server.rs:209-216` `display_text` drops `char::is_control` (Cc) and cuts to 60 characters; bidi overrides (U+202A-202E, U+2066-2069), zero-width characters and U+FEFF pass, while the extension's own `displayText` (`limits.ts:40-42`) removes them. A site can register a passkey whose name reorders the later "Replace your passkey?" text (the site id is the validated rp id, so it cannot be faked). Distinct from V7. **RA-8 (Info): any page can make the extension connect to LocalPass, and can see that the extension is installed.** A `navigator.credentials.get/create` call with no gesture reaches `usable()` (`content/passkeys.ts:79-87`), which sends `findLogins{interactive: true}`; the worker connects and, if the app is not running, the helper starts `localpass.exe --minimized` (`nmhost.rs:97-98`, `native_host.rs:19-40`). **RA-9 (Info): answer to the open question in notes 5.5b ("`Server::verified` asks Hello for anything but discouraged, whatever the setting says").** Intended and safe. `server.rs:684-699`: Hello is skipped only when this request made the user unlock (`just_unlocked`) or when the site says `discouraged` and "Ask Windows Hello for every passkey sign-in" is off; `preferred` and `required` always ask, which matches WebAuthn and the label "Even when a website says it doesn't need it". Nothing to change; the e2e helper uses `discouraged` for exactly this reason.

**Read and found sound.** Read in full: `background/{broker,storage,index,passkeys}.ts`, `content/{ui,index,passkeys,validate,detect,inject,ask}.ts`, `shared/{limits,crypto,protocol,messages}.ts`, `manifest.json`, `build.ts`, popup (lists and fill), `lp-broker/src/{server,framing,clients,protocol}.rs`, the helper (`nmhost.rs`) and the app's `broker.rs` host. Sound: the TypeScript handshake cannot reach `trusted` without this connection's challenge, nonces and a matching proof, and a reordered, repeated or unsolicited `challenge`/`ready`/`paired`/`unpaired`/`denied` closes the port; reflection is impossible because the labels differ at the start of the HMAC input; the Rust side matches (fresh 32-byte server nonce, `ct_eq`, client nonce must be 32 bytes, a known id can only authenticate, never re-pair); revocation is re-checked at the top of `dispatch`, after the unlock and after every user check, plus the broadcast close; a provider client is limited by `allowed_for_provider`/`provider_only` and `userVerified` is overwritten; limits (32 handshakes and 16 sessions in separate pools, 16 in flight, 15 minutes idle, 10 s half-message, one user check at a time, `tooLarge`) behave as documented and an unauthenticated peer cannot take a session slot (a client that holds a secret can still use all 16, accepted in the comment); the manifest has no `externally_connectable`, `web_accessible_resources` or host permissions; `dist` is built without `--e2e` (`mode: "closed"`, no `__E2E__`) and the app bundles only `extension/dist`; page text reaches the DOM only through `textContent` and `displayText` (no `innerHTML`, `document.write` or clipboard use in `src`); both `message` listeners require `event.source === window`; `validate.ts` re-checks every field, so a page getter that returns different values on a second read cannot get past it; `limits.ts` equals the engine's numbers (256 characters and entries, 1023-byte ids, 64-byte handle, 253-character rp id; JS counts UTF-16 units, so it is never looser); same-origin rule for frames holds and fails closed. Design residual (not new, tied to the open README trust-boundary decision): the origin is asserted by the client, so a process that holds the extension secret can still `findLogins`/`fillLogin` any site it names without a prompt; V5 only covers `force` and `searchItems`.

**RB-3 (Low, ran for AES rounds, read for Argon2): KeePass import has no key-derivation limits; V15 fixed only `.lpbackup`.**
- Where: `import_export.rs:57` -> `crates/lp-import/src/keepass_import.rs:22` (`Database::parse`) -> keepass 0.15.2 `src/crypt/kdf.rs` (`for _ in 0..self.rounds` with a u64 from the file; Argon2 `mem_cost: (self.memory / 1024) as u32`, `time_cost: self.iterations as u32`, lanes from the file). `commands.rs:546-567` runs it with `spawn_blocking`, which cannot be cancelled.
- Scenario: the user imports a `.kdbx` from an untrusted source and types any password. The header asks for 2^50 AES rounds: one core spins until the app is quit and the dialog says "Importing...". With a huge Argon2 memory the allocation fails and the app aborts (an allocation failure is not a catchable panic). Confidentiality is not affected.

**RB-4 (Low, ran and read): the LAN sync listener has the pre-authentication pool problem V8 fixed for the broker.**
- Where: `crates/lp-sync/src/service.rs:38` (`MAX_INBOUND = 8`), `:510` (permit taken before a byte is read), `:864-870` (5 s preamble wait), `channel.rs:24` (5 s handshake); pairing: `service.rs:1018` (`pairing.try_lock()`), `pairing.rs:39` (15 s per step), `service.rs:1048-1081` (only `WrongCode` counts toward the 3 tries; `Other` does not).

### Left, with the reason

Fix before release (5.5): **RB-8 / RC-4** the NSIS uninstall hook does not remove the browser registration keys or the provider's data and
removes the package even when `unregister` failed (needs an installer build and a throwaway-user uninstall to check, so

fetched, and diff against Google's current list; the unused `assets/extension/` copy in the APK.

Known limits to state in the README (5.4): **RB-3** a hostile `.kdbx` can demand unlimited key-derivation work (import only files you
trust; fix = read the KDF parameters from the header and apply the backup limits); **RB-4** (rest) a host on the LAN can still stall one
pairing attempt for 15 s at a time; **RB-5** (rest) if the broker pipe cannot be created the app logs it once and does not retry or tell the
user; **RC-6** the passkey list Windows keeps in its own cache (site, user name, credential id) can be read by any process of the same
user, also while the vault is locked; **RC-3** the provider's files, alias and `AppPath` are user-writable (same-user, outside the vault's
threat model); **RC-8** the provider's COM server accepts any process of the user, `CancelOperation`/`GetLockStatus` need no signature and
the provider log names sites; **RC-2** a passkey the app created is kept when Windows or the browser cancels at the last moment.

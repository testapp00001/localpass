# Phase 5 hardening notes (written 2026-10-19, read-only review)

Method: every claim was checked against the code. `[R]` = read in the code at the cited line. `[X]` = also
confirmed by running a throwaway program outside the repo (`lp-core` as a path dependency, offline; nothing in the
repo changed). The repo has no commits, so "the diff" for the final review is the whole tree.
Path shorthands: `KT` = `app/src-tauri/gen/android/app/src/main/java/app/localpass`, `APP` = `app/src-tauri/src`,
`EXT` = `extension/src`, `BR` = `crates/lp-broker/src`.
Trust labels: WEB = any script on a page (incl. third-party scripts/XSS); EXT = the extension's own code;
LOCAL = any process of the same Windows user; APP = another Android app; PEER = paired device after Noise; FILE = user-chosen file.

## 3. Concrete test plan

Dev-dependencies: `proptest = "1"` is already in the root `[workspace.dependencies]` and in `lp-core` dev-deps. Add
`proptest.workspace = true` under `[dev-dependencies]` of `crates/lp-broker/Cargo.toml` and `crates/lp-engine/Cargo.toml`.
No `arbitrary` crate is needed: use `proptest::collection::vec(any::<u8>(), 0..N)` and `prop::string::string_regex` for random bytes and strings;
mutate valid inputs (flip/insert/delete a byte) for structure-aware cases. `tokio` already has `test-util` in both crates.
Run everything under plain `cargo test -p <crate>`. Commit `proptest-regressions/` (it is not git-ignored). Use
`ProptestConfig { cases: 256, .. }` by default; CI may raise `PROPTEST_CASES`. Never build an `Engine` per case (Argon2): create one vault outside `proptest!`
and share it. `[F]` = expected to fail today (it documents a defect from section 5, then passes after the fix).

### 5.5 Phase 5.2 part A (Rust side) done 2026-10-21: what changed, protocol, follow-ups

Broker protocol changes (all backward compatible: no request or reply field was removed or renamed):
- New error codes in answers: `tooLarge` (the answer did not fit in a 1 MiB frame), `tooMany` (more than 16 requests in flight on one connection, or, in the handshake, more than 16 open connections), `unpaired` (the client was removed while the request ran). `denied` now also means "the user declined to replace what is saved".
- `searchItems` and `fillLogin{force:true}` for a login that does not match the page now show a Windows Hello prompt each time (can take up to 120 s, answer `denied` if declined). `searchItems` lists live logins only (no notes, cards, passkeys, trash). `fillLogin{force:true}` refuses a trashed item or a non-login with `notFound`, a bad page with `invalid`, both before anybody is asked. A forced fill for a login that does match the page still fills silently.
- `saveLogin` that would change an existing login (same host, or another address of the same site) waits for an in-app dialog (up to 120 s) and answers `updated` or `denied`; new logins and unchanged ones answer at once as before. `passkeyCreate` for a site and user handle that already has a passkey does the same before Windows Hello, and `denied` leaves the old passkey in place.
- A connection that sends nothing for 15 minutes is closed; the helper and the extension reconnect on the next request.

Follow-ups for the other agents:
- Extension (TS): the popup's "search all items" must not search per keystroke (each call is a Hello prompt): fetch once on an explicit action (limit up to 200) and filter in the popup, and explain the Hello prompt; handle `denied` from `fillLogin{force:true}` and `searchItems` quietly. The save flow: `saveLogin` can now take up to two minutes and answer `denied` ("you chose not to replace"): show that, and do not retry. `passkeyCreate` may answer `denied` for the same reason (treat like a cancelled Hello). Handle `tooMany` / `tooLarge` as an ordinary failure. A connection closed after 15 idle minutes or because the client was forgotten (then the next handshake says `unpaired`) must trigger the normal reconnect path.
- Android (Kotlin): `provider::call("saveLogin")` no longer updates a login saved for another host of the site (it makes a new login); same host still updates in place. No Android confirmation exists for either case (the system Save sheet is the user's yes). `passkeyCreate` through Credential Manager still replaces a passkey of the same account silently (the system sheet is the yes); `Engine::passkey_would_replace` can be exposed as a provider op if a warning is wanted.

Numbers: handshakes 32, sessions 16, in flight 16 per connection, idle 15 min, half-sent message 10 s, key derivation memory <= 512 MiB, passes <= 10, lanes <= 8, passkey text 256 characters, id lists 256 entries, credential ids 1023 bytes, `searchItems` limit <= 200.

### 7.2 What the lp-sync properties check (`replica_props.rs`)

One world: genesis, `P adds W1`, `P adds W2`, three data ops each for P, W1 and W2, and a stranger. The properties shuffle,
duplicate, cut, chunk and corrupt it.

- Any order, batch size and repeat converges to exactly the history: nothing rejected, nothing staged, no fork.
- Any subset leaves a gapless log, a member's op is stored only after the roster op that introduced the member, and no
  placeable op stays staged (`accepted + staged == unique delivered`).
- A stranger's ops stay staged and never reach the store; ops for another vault are rejected.
- A bad signature is rejected, leaves no trace, and the genuine op sent next is accepted.
- Every one of the 94 x 8 bits of a signed header, flipped with the signature kept, is never stored (exhaustive, not
  sampled, because a random byte mostly lands on the author, vault or hash fields).
- A second validly signed op at a stored (author, seq), roster or data, is reported as a fork, is not written, does not
  bump `version()` and never changes the roster (a forked `Genesis` or `DeviceAdded` naming the stranger does not make the
  stranger known).
- `ops_missing_for` is exactly the suffix beyond the peer's vector, for any claim including `u64::MAX` and unknown authors;
  the missing ops bring any partial replica up to date in any batch size and order, and a second request finds nothing.
- `verify_peer`: a stranger's key is never accepted with any proof of 0 to 20 ops drawn from valid, foreign-vault,
  data-class and bad-signature ops; an unknown member's key is accepted exactly when the proof has its `DeviceAdded` and no
  invalid op (duplicates and any order included); more than `MAX_PROOF_OPS` is a protocol error; a key already in the roster
  needs no proof. A device's own `membership_proof` is enough for a replica that has only the genesis op.

Mutation check (production code broken on purpose, then restored byte for byte): with the signature check in `ingest`
disabled and the gap check loosened at the same time, five of the ten tests failed; with only the signature check disabled,
the exhaustive header test fails too.

**Pinned observation (not a vulnerability):** `ingest` drops a repeat of an op by (author, seq) and header before it
verifies signatures, so a forged copy that comes first in a batch shadows the genuine op for that batch. The version vector
does not move, so the next sync sends the op again, and a peer that sends forgeries could have withheld the op anyway.
`a_forged_copy_ahead_of_the_real_op_in_one_batch_shadows_it_until_the_next_sync` pins it.

### 7.3 What the lp-winauth properties check (`translate_props.rs`)

- `origin_for` accepts exactly the plausible host-like ids and builds `https://{id}` and nothing else (no userinfo, port,
  path, backslash, space, NUL, bidi or full-width dot gets in). For whatever it accepts, `Origin::parse` plus the engine's
  `validate_rp_id` only accept the id when it is the host itself, never for an address the URL parser made out of a numeric id
  (`0x7f.1`, `2130706433`, `1.10`): the provider sends such ids on and the engine refuses them. If either side changes, this
  fails.
- `create_request` decides in a fixed order (RP id, ES256 present, user id 1 to 64 bytes), passes every field through
  unchanged and never sets `user_verified`.
- `assert_origin`: Ok exactly for a 32-byte client data hash and an accepted RP id.
- `created_parts`: the honest answer is accepted; another RP, a changed credential id, any cut of the authenticator data, a
  missing attested credential and random bytes are all errors.
- `check_assertion`: Ok exactly when the RP hash matches, the credential is on the allow list (or there is none) and the
  signature is not empty.
- `cache_row` keeps ids and names and fills an empty RP name and display name; `hresult_for` follows the documented table for
  every `RelayError` variant (a wildcard-free `match`, so a new variant must be classified first) and never returns a success.
- Mutation check: allowing `/` in `origin_for`, skipping the allow-list check and skipping the RP-hash check, all three at
  once, made four of the eight tests fail (the rest only restate `origin_for` and are not meant to catch that).

Not covered on purpose: `MakeRequest::from_decoded` / `GetRequest::from_decoded` on random bytes would feed garbage to
Windows' own `webauthn.dll` decoder (request signature is verified by the handler first, and the decoder is Microsoft's).
The captured webauthn.io request and the hand-built malformed ones in `translate.rs` and `sys` cover our side of it.

### 7.4 Pinned behaviour found by the other property files (decisions, not defects)

- S7: a frame header cut after 1 to 3 bytes reads as a clean close (`framing_props.rs`).
- V22: a saved URL without a port matches every port; with a port it matches only that port (`origin_props.rs`).
- base64url padding is accepted and dropped (`passkey_props.rs`).

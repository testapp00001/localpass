# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

LocalPass is a fully local password manager. The vault lives only on the user's devices (Windows desktop and Android phone) and syncs directly between them over the LAN. There is no server, account, telemetry or updater, and none should be added. The README has the user-facing overview and threat-model notes.

### Android

- Env needed in each shell: `JAVA_HOME` (Android Studio's `jbr`), `ANDROID_HOME`, `NDK_HOME` (NDK r27d `27.3.13750724`). The four Rust Android targets are in `rust-toolchain.toml`.
- `bun run tauri android build --debug --target aarch64 --apk` (or `... android dev` for a USB-connected phone). On Windows this compiles the Rust library but then fails creating a symlink unless Developer Mode is on.
- Without Developer Mode: copy `target/<triple>/debug/liblocalpass_lib.so` into `app/src-tauri/gen/android/app/src/main/jniLibs/<abi>/`, then in `app/src-tauri/gen/android` run `gradlew.bat assembleArm64Debug -x rustBuildArm64Debug` (flavours: `Arm64`, `X86_64`, ...).
- Quick Rust-only check: `cargo clippy -p localpass --target aarch64-linux-android -- -D warnings` (a cold build is slow; run it in the background). It needs the CC/AR/linker env vars pointing at the NDK's `aarch64-linux-android24-clang.cmd` / `llvm-ar.exe`.
- QR scanning (`app/src/lib/scan.ts`): `cd app && bun test test/scan.test.ts` (fake plugin) and, on `lp_api37`, `cd extension && bun run e2e/android-scan.ts [debug apk]` or `... --release <apk>` (Cancel, Back, reopen; start the emulator with `-camera-front emulated`). The plugin's `cancel()` never settles a pending `scan()`, so never rely on that promise to end a scan. A web view's accessibility tree does not follow scrolling: e2e steps must not scroll (submit forms with Enter).
- Releases: the Android versionCode comes from `tauri.conf.json` `version` (major*1000000 + minor*1000 + patch: 0.1.1 -> 1001, 0.2.0 -> 2000); keep it equal to the root `Cargo.toml`, `app/package.json` and the extension's `manifest.json`/`package.json`. There is no updater: a release is the NSIS installer, the signed APK, the extension zip and a `SHA256SUMS.txt`, installed over the old version by hand (README, "Installing and updating"). Releases are built by GitHub Actions: `bun scripts/release.ts X.Y.Z` bumps the five version files, regenerates `CHANGELOG.md` (git-cliff, `cliff.toml`, Conventional Commits), commits and tags, and pushing the tag runs `.github/workflows/release.yml`, which leaves a draft release (README, "Making a release"). Settings only has a "Releases" link that opens the GitHub page in the browser; the app never contacts GitHub itself. Windows-only bundle settings (the extension folder, the provider package, the uninstall hook and script) live in `tauri.windows.conf.json`, so nothing of them ends up in the APK.
- Release APK: `bun run tauri android build --target aarch64 x86_64 --apk --ci`. Gradle signs it from `gen/android/keystore.properties` (git-ignored; the key lives outside the repo). R8 is off in `app/build.gradle.kts` on purpose (it broke WorkManager's Room database at startup). Release builds have no WebView debugging (the library has no call that enables it; the userdebug emulator image opens every web view to DevTools regardless), so drive them with `adb shell uiautomator dump` and `input tap/text`: `cd extension && bun run e2e/android-release.ts <path to the apk>` is the release smoke test on `lp_api37` (it uninstalls any debug build first, installs the APK, creates a vault, uses the set-up section, saves, fills and makes a passkey; the other `e2e/android*.ts` scripts read the app through its debug web view and need a debug build); debug builds can be driven over Chrome DevTools (`adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`).
- Android 17 (target SDK 37) asks for the local-network permission at startup; grant it or sync and pairing are blocked. In Git Bash, prefix adb commands that take `/sdcard/...` paths with `MSYS_NO_PATHCONV=1`.
- The emulator cannot see the LAN. Real pairing/sync tests need a physical phone; the emulator can still reach the host at `10.0.2.2`.
- Passkeys and autofill on a real system image (needs an emulator with Chrome and an enrolled fingerprint, e.g. AVD `lp_api37`, unlocked): build with `cd app/src-tauri/gen/android && ./gradlew.bat :app:assembleX86_64Debug -x rustBuildX86_64Debug` (after a `tauri android build` has produced the `.so`), then `cd extension && bun run e2e/android.ts` (`LP_SKIP_INSTALL=1` reuses the installed build); `bun run e2e/android-save.ts` does the same for saving a login from Android's autofill prompt. It drives Chrome over DevTools, the system sheets with uiautomator (`e2e/adb.ts`), and the app's WebView; it changes the credential/autofill provider settings and restores them. The first start after an install can raise a false "isn't responding" box on the software-rendered emulator; the helpers tap Wait. `bun run e2e/android-nolock.ts` checks the refusal on a phone without a screen lock; it needs the PIN removed first (`adb shell locksettings clear --old 1234`), which also deletes the enrolled fingerprint, so copy the AVD's data files (everything but `snapshots`) beforehand and copy them back with the emulator stopped. Do not leave stale system sheets or fingerprint prompts open between runs (`am force-stop app.localpass`), they swallow the next run's touches.
- Kotlin unit tests (trusted-browser decision): `cd app/src-tauri/gen/android && ./gradlew.bat :app:testX86_64DebugUnitTest -x rustBuildX86_64Debug`. The in-app "Autofill and passkeys" set-up section (Settings, Android only; `app/src/screens/AndroidSetup.tsx`, Kotlin `LpMobilePlugin.setupStatus/openSetup`, commands `android_setup_status`/`android_open_setup`) is checked by `cd extension && bun run e2e/android-setup.ts`. Android hides from apps whether LocalPass is the passkey provider (`credential_service` is not readable), so that row shows no status on purpose.
- `.cargo/config.toml` links Android libraries with 16 KB page alignment; don't remove it, or the library won't load on newer phones.

## Architecture

Crates layer upward: `lp-core` → `lp-store` / `lp-sync` → `lp-engine` → front ends (`app/src-tauri`, `lp-cli`, the Android JNI entry points). `lp-import` feeds `lp-engine`.

- **lp-core**: pure logic, no I/O. Crypto, the signed op format, HLC, the CRDT materializer, the device roster rules, password generator, TOTP. `KdfParams::insecure_for_tests()` (behind the `test-utils` feature) makes Argon2 fast; tests must use it.
- **lp-store**: SQLite op-log, metadata, peer address book.
- **lp-sync**: Noise transport, sync protocol, ingest rules (`replica.rs`), SPAKE2 pairing, mDNS discovery, and `service.rs`, which runs the listener, scheduler and address book.
- **lp-engine**: the single `Engine` facade (vault lifecycle, items, devices, import/export, sync start/stop). Everything above it calls only this. `credentials.rs` is what browsers and OS providers use: `find_logins`/`fill_login`/`save_login` and the passkey calls (`passkey_create`, `passkey_candidates`, `passkey_assert`). They re-validate the origin and sign inside the engine, so private keys never leave it. The one exception is the encrypted backup (`export_backup`, restored by `import_file`), which carries passkeys with their private keys inside the sealed file; the plain JSON export leaves passkeys out and `passkeys_left_out_of_plain_export` counts them.
- **lp-broker**: how the browser extension (and later the Windows passkey provider) reaches the running app. Length-prefixed JSON over a per-user Windows named pipe (`pipe.rs`, user-only DACL, remote clients refused), a handshake that pairs a client once (user approves a 6-digit code in the app) and then proves the shared secret in both directions (`server.rs`), requests in `protocol.rs`, and `nmhost.rs`, the native-messaging helper that just relays stdio to the pipe. The app supplies prompts through the `Host` trait (`app/src-tauri/src/broker.rs`). Cargo features: `server` (the app side: request handling against the engine, the pipe listener, `nmhost`) and `client` (a Rust client, `client.rs`: handshake with server-proof check, pairing, requests; no engine, sync or store dependency, so `--no-default-features --features client` is what the provider links). Both are on by default. The request/response DTOs (`PasskeyCreateRequest`, `PasskeyCandidate`, ...) and `VaultStatus` live in `lp-core` so the client can use them; `lp-engine` re-exports them. A dropped connection aborts that connection's pending unlock/Hello/pairing prompts, so open one connection per cancellable operation. **Revocation:** `Broker::revoke(client_id)` (via `BrokerState::forget_client` in the app, which every "forget" path uses) closes a forgotten client's connections and drops its prompts, and every request and user prompt re-checks the client store anyway. **Revealing other sites' logins:** `searchItems` and `fillLogin{force}` for a login that does not match the page call `Host::verify_user` every time (Hello, no policy exemption, no "just unlocked" shortcut). **Overwrites:** `saveLogin` that would change a saved login (`Engine::plan_save_login` says so) and `passkeyCreate` that would replace a passkey (`Engine::passkey_would_replace`) call `Host::confirm_overwrite`; the app shows the in-app "Replace?" dialog (`UiEvent::ConfirmOverwrite`, answered with `broker_respond`) and a no answers `denied`. **Limits:** 32 handshakes and 16 sessions (separate pools), 16 requests in flight and 15 minutes idle per connection, user checks one at a time, answers over 1 MiB become `tooLarge`, `KdfParams::validate` caps backup header costs.

Design points that span several files:

- **Event-sourced CRDT.** Each device appends signed ops to its own gapless log (`seq` 1, 2, ...). Devices swap version vectors and send missing ops, and any device relays any other device's ops. Fields merge last-writer-wins by hybrid logical clock, and overwritten values are kept as history. Concurrent edits (same `base`) are flagged as conflicts. Unknown op variants must be stored and relayed, not rejected.
- **Sync never needs the vault key.** Data bodies are XChaCha20-Poly1305 ciphertext; sync only verifies Ed25519 signatures and moves bytes. That is why sync runs while the vault is locked, including from the Android background worker. Keep decryption out of `lp-sync`.
- **Store and verify exact bytes.** Op headers are fixed-size, the signature covers the header, and the header contains the body hash. Never re-serialize an op before verifying or relaying it.
- **Transitive trust.** Membership is a chain of signed roster ops (`Genesis` → `DeviceAdded` ...). Each Hello carries a membership proof, so two devices that never met (for example a work laptop and a home laptop) can accept each other. Revocation uses a `cutoff_seq` and does not cascade.
- **Key protection.** Per-device master password → Argon2id KEK wraps the vault key and signing key. A separate device secret (DPAPI on Windows, Android Keystore) protects the network key and the Noise key, so the sync stack can start without the master password.
- **Fully local networking.** The dialer only targets private and link-local addresses. mDNS uses random names and hourly-rotating member-only tags. Don't broadcast device names.
- **Pairing** is an 8-digit code (or QR) run through SPAKE2, at most 3 failed tries, plus explicit approval on the inviter.
- **Origins come from the browser or OS, never from page content.** `lp_core::origin` matches saved logins by registrable domain (compiled-in public suffix list; https only, http for localhost) and validates WebAuthn relying party ids. Passkeys are ES256, stored as vault items (`kind = passkey`, fields `passkey.*`, private key marked secret), with signature counter 0 and the backup flags set, so they sync like any item.
- **`localpass.exe` is also the native-messaging helper.** When a browser starts it with an extension origin as the first argument, `main.rs` runs `native_host` instead of the app. The browser finds it through HKCU registry keys written by Settings → Browser extension (`native_messaging.rs`). The extension id is fixed by the `key` in `extension/manifest.json`; `lp_broker::nmhost::EXTENSION_ID` must match it.

- **The extension wraps WebAuthn in the page.** `inject.ts` runs in the page's MAIN world and replaces `navigator.credentials.create/get`; it talks to the isolated content script (`content/passkeys.ts`) with `window.postMessage` (checked with `event.source === window`). The content script asks the user (dialog, or the username field's menu for conditional mediation), the service worker adds the origin from `sender`, and the engine signs. Anything LocalPass declines (security keys, other algorithms, no match, switched off in the popup, app unreachable) goes back as `fallback` and the page uses the browser's own flow. `content.js` runs at `document_start` so the bridge exists before the page's scripts: it must not assume the DOM is parsed (rescan in `formOf`, wait for `DOMContentLoaded` before offering a save), and the service worker sleeps when idle, so passkey calls may connect to the app rather than treat "not connected yet" as "unavailable". `e2e/run.ts` and `e2e/passkeys.ts` catch both.
- **Firefox build (Phase 6.6).** `bun run build --firefox` (manifest from `manifest-firefox.ts`; `__FIREFOX__` is a build-time define, tests flip `globalThis.__FIREFOX__`). Firefox has no IntersectionObserver `isVisible` and no `storage.local.setAccessLevel`, so: the pairing secret and other persistent data live in an IndexedDB area of the extension origin (`background/storage.ts` `local()`; the popup uses it too, nothing else may touch `chrome.storage.local`), and every decision an in-page control makes in Chrome is made in an extension-owned window (`background/decide.ts` + `src/decide/`; the background builds the site from `sender`, the window gets no secrets, `authorize()` checks the window). Details and measurements: `docs/handoff-phase6-linux.md`, 6.6.
- **Extension trust rules (Phase 5.2).** The service worker reaches `chrome.storage.local` only through `background/storage.ts` `local()`, which first restricts the area to trusted contexts (content scripts can read `storage.local` otherwise: they ask the worker, e.g. `passkeysEnabled`, and never touch `chrome.storage`; `test/storage.test.ts` scans for it). `BrokerClient` trusts a connection only after this connection's challenge and a matching server proof (one `Connection` object per port); anything else closes the port. Whatever a page posts goes through `content/validate.ts` and the limits in `shared/limits.ts` (same numbers as the app) and is shown only through `displayText` and `textContent`; a call over a limit falls back to the browser. `doFill` carries the origin it was fetched for and the page checks it. The popup fetches all logins once per click (`loadLogins`, one Windows Hello prompt) and filters locally; unit tests use the fakes in `extension/test/chrome.ts` and `fakeapp.ts`.

### Desktop / mobile app (`app/`)

- `app/src-tauri` is crate `localpass` (lib `localpass_lib`). `lib.rs` wires state, the tray, close-to-tray, the auto-lock loop and plugins. `commands.rs` holds the ~40 Tauri commands. A new command needs three edits: the function, `tauri::generate_handler!` in `lib.rs`, and a typed wrapper in `app/src/lib/api.ts`.
- Secrets stay in Rust. Item lists never carry passwords to the webview, and copying to the clipboard happens in Rust (`clipboard.rs`).
- Engine events reach the UI on the `lp-event` channel, and `App.tsx` re-dispatches them as DOM events (`lp-vault-changed`, `lp-sync`, `lp-paired`) that screens listen for.
- Platform code is gated by `cfg`: `hello.rs` (Windows Hello) on Windows; tray, autostart and single-instance on `desktop`; `android.rs` and `mobile.rs` on Android. A change to shared code must still compile on both desktop and Android.
- **Prompts for a browser or Windows (desktop).** The app sits in the tray, so a Windows Hello check that a broker client causes (`AppHost::unlock`, `verify_user`) first gets the foreground through `focus.rs` (a 1x1 transparent `Anchor` window plus the steps in `bring_to_front`), otherwise Windows only flashes a taskbar button; `show_main` runs the same steps as a logged backstop for the main window (the pairing dialog). The unlock screen must not start Hello by itself while the window is hidden (`unlock_quick(auto)` answers `"hidden"`; the UI retries on `windowShown`, sent only when the user opens the window): the broker request owns that prompt, and two Hellos appeared before. Both write `lp_prompt` events to `<data dir>\prompts.log` (`applog.rs`; window class, exe name, ids, no titles or vault data).
- **Windows passkeys (desktop).** Settings > Windows passkeys (`app/src-tauri/src/windows_passkeys/`) registers `crates/lp-winauth` as a Developer Mode loose package from the `windows-passkeys` resource folder (staged by `app/scripts/stage-provider.ts` in `build:all`, shipped by `tauri.windows.conf.json`, which also holds the NSIS uninstall hook `windows/hooks.nsh`, which runs `windows/uninstall-cleanup.ps1` from the install folder before the files go: it removes the browser keys only when their manifest names this install's exe, unregisters the provider and leaves the package registered when `unregister` fails (exit 3, the uninstaller then tells the user), only touches a package registered from this install folder, and deletes the provider data with the "delete app data" box; every path comes in an environment variable so `app/test/uninstall-cleanup.test.ts` runs the real script against throwaway keys and folders) and drives the provider's `register|unregister|status|pair|sync-cache` through its execution alias; the steps run behind a `CommandRunner` trait (PowerShell only for Get/Add/Remove-AppxPackage, values passed as environment variables, never in command lines), `unregister` must precede `Remove-AppxPackage`, and never run setup/remove tests against the real package identity (use the `test-identity` feature of lp-winauth and the debug-only `LOCALPASS_PROVIDER_*` variables, see the notes, "Phase 4.5").
- **Android path.** Kotlin in `app/src-tauri/gen/android/app/src/main/java/app/localpass/` is hand-written and committed (the sibling `generated/` folder is not). `MainActivity` hands the data dir and Keystore-protected device secret to Rust through `NativeBridge` (JNI, implemented in `android.rs`). `SyncWorker` (WorkManager) calls `runSyncOnce` while the app is closed. `LpMobilePlugin` provides the sensitive clipboard and biometric unlock, which Rust reaches through `mobile.rs`. Commands that call into Kotlin must not run on the main thread, because the plugin call blocks.
- **Android credential services.** `LpCredentialProviderService` (Credential Manager, Android 14+) and `LpAutofillService` run in the app's process, which Android may start without the UI. Kotlin sends one JSON request per call to `NativeBridge.credentialCall`, which `android.rs` hands to `lp_engine::provider::call` (the requests are listed there; WebAuthn JSON translation is in `webauthn_json.rs`). All of the process's users share one engine from `android::open_engine`, because two engines over one database don't see each other's changes. When only the services use the vault, `lock_later` locks it a minute after the last request; once the UI has started, the UI's own loop decides. The website comes only from `CallingAppInfo.getOrigin` with the bundled `assets/privileged_browsers.json` (Google's trusted-browser list), pinned by SHA-256 in `BrowserTrustTest` (a copy of https://www.gstatic.com/gpm-passkeys-privileged-apps/apps.json, byte-identical on 2026-10-23; to change it fetch it again, read the diff, update the digest), so non-browser callers get nothing; responses omit `clientDataJSON` because the browser supplies its own hash. `CredentialActivity` and `AutofillActivity` (translucent, `FLAG_SECURE`) do the unlock and fingerprint checks; an unlock carries over once to the passkey pick that follows it only through `UnlockCarry` (a single-use token for that website, 30 s, issued only by `CredentialActivity`'s own unlock step and carried in the entries it returns, so an autofill or save unlock never counts; a fingerprint for one passkey never carries to another). **Passkeys need a screen lock:** `PasskeyPolicy.refusal` (`isDeviceSecure` plus a biometric/credential check that can answer) makes `CredentialActivity` show "Set a screen lock to use passkeys" and fail the request with `NotAllowedError` before any unlock, so `userVerified` is always true when a passkey op runs; Settings shows a warning row from `setupStatus.screenLock`. **Replacing:** `create()` asks the provider op `passkeyWouldReplace` (`Engine::passkey_would_replace`) and shows "Replace your passkey?" before the biometric prompt. **Shown text:** prompts and system entries show the engine-checked relying party id first (`ShownText.site` keeps the right end of a long host), page-supplied names are cut and stripped of control and bidi characters (`ShownText.clip`). **Device secret:** `DeviceSecretStore` deletes the stored secret only for a permanent failure (`DeviceSecretFailure.isPermanent`: key gone or changed, bad tag, damaged file); anything else is retried and then `Unavailable` (`LpProvider.call` answers `keyStoreUnavailable`) and the secret stays. The FileProvider (`res/xml/file_paths.xml`) shares only the app's `Pictures/` folder in external files. Autofill datasets have no values until the user picks one (the dataset's authentication fetches that login). The autofill service acts (fill, authenticate, save) only when the app in front is a browser on that same list: `BrowserTrust.kt` checks the `AssistStructure`'s activity package and its signing certificate SHA-256 against the bundled JSON (`parse`/`isTrusted` are pure and unit-tested in `app/src/test`; installed packages are visible through `<queries>` for https browsers in the manifest), otherwise no datasets, no unlock row and no `SaveInfo`. `AutofillActivity` re-checks from the `AssistStructure` the system adds to the intent (`checkedForm`: trusted browser, and its website equals the extra), never from extras alone. What remains: the trusted browser reports the page's domain and LocalPass trusts it; unlisted browsers and native apps get nothing. **Saving:** a `FillResponse` for a form with both a username and a password field carries a `SaveInfo` (a response with only that when no login matches; an unlock or pick returns a new response that repeats it), and `onSaveRequest` reads the typed values with `AutofillParser.typed` (website from the same unverified `webDomain` as filling) and calls the `saveLogin` op (`Engine::save_login`: new item, updated password or unchanged, never a duplicate). With a locked vault the password waits in `PendingSaves` (memory only, random token, 2 minute life, wiped on use) while `SaveCallback.onSuccess(IntentSender)` (API 28+) opens `AutofillActivity` (`ACTION_SAVE_LOGIN`) for the usual unlock; below API 28 a toast says nothing was saved. Emulator test: `extension/e2e/android-save.ts`.
- UI threads (Tauri commands, JNI) call the engine from outside any tokio runtime, so code reachable from sync engine methods must not use `tokio::spawn`; `SyncService` keeps a runtime `Handle` for that. JNI function names must match the package `app.localpass`.

## Conventions

- Rust edition 2024, `rustfmt.toml` max width 100, clippy `-D warnings`. Dependencies are declared once in the root `[workspace.dependencies]`.
- `[profile.dev.package."*"] opt-level = 2` keeps Argon2 and Noise usable in debug builds.
- Scenario tests bind `127.0.0.1` with mDNS off, so they need no network access.
- Use `encoding="utf-8"` when editing files from Python on Windows.
